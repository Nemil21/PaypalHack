## HF-014: Bid service: `POST /bids` with card and vaulted holds
- **[BLOCKER]** Race with Clear can leave a hold dangling. Step 2 checks the listing is biddable, then the PayPal call takes 1–3 s, then step 6 sets PENDING_APPROVAL→HELD. If Clear flips the listing to CLEARING in that gap, Clear's `SELECT … WHERE status='HELD'` misses the bid. The bid then becomes HELD on a CLEARING listing, is never settled, and is only voided by the *nightly* sweeper once the listing reaches SETTLED. That breaks feature 10's P0 acceptance ("Concurrent place_bid during Clear is rejected with WINDOW_CLOSED") and the 16 concurrency test. → Do the final PENDING_APPROVAL→HELD transition in a new transaction that first runs `SELECT status, window_closes_at FROM listings WHERE id=$1 FOR SHARE`. (Clear's `UPDATE … SET status='CLEARING'` takes a row lock, so the two serialize.) If the listing is no longer biddable, commit the bid as VOIDING and void the fresh authorization at once (`void_reason=WINDOW_EXPIRED`). Add an integration test with a hook that pauses between the PayPal response and finalize while Clear runs.
- **[BLOCKER]** Two live bids from one shopper on one listing can both win, so the shopper is charged twice. "Second bid → route to raise" lives in application code only. Two tabs, or the offer page plus the agent, or a retry with a new Idempotency-Key, each pass the check and create two HELD bids. Both rank, both can WIN, and the shopper is captured twice for two units they never asked for. → Take `pg_advisory_xact_lock(hashtext(shopper_id||listing_id))` around the "existing live bid?" check and the insert. Add a DB backstop: `CREATE UNIQUE INDEX one_held_bid ON bids(listing_id, shopper_id) WHERE status='HELD'`. With the atomic swap in HF-018, the index holds even during raises.
- **[BLOCKER]** The CARD path as written isn't the browser card-fields flow. The ticket and api.md say CARD → `201 HELD` straight from `POST /bids`. That's only true for the spike pattern, where our server sends the raw card number. With JS SDK v6 card fields (required by HF-019, "card data must not touch our API"), the flow is:
  1. our server creates an `intent: AUTHORIZE` order with no card data;
  2. card fields submit the card to PayPal, possibly with a 3DS contingency;
  3. our server calls `POST /v2/checkout/orders/{id}/authorize`.

  So CARD is a two-step flow like PAYPAL, and it's untested. → Make CARD return `201 {bidId, status: PENDING_APPROVAL, orderId}`. Add `POST /api/bids/:id/authorize` (the shared approve-and-finalize path with HF-015's return handler) that calls `pp.authorizeOrder` with a deterministic request id. Set `payment_source.card.attributes.verification.method=SCA_WHEN_REQUIRED` and `attributes.vault.store_in_vault=ON_SUCCESS` on create, and read `vault.id` from the authorize response. Allow raw `payment_source.card` only from server-side seed/test code (HF-045 SIM holds), never from request input. Run a 30-min sandbox spike (S7) of the v6 card-fields + vault + authorize flow before building HF-019.
- **[MAJOR]** If the PayPal call times out after PayPal succeeded, the hold dangles. The bid stays PENDING_APPROVAL, and HF-034's abandon cron marks it ABANDONED "no hold exists", but for VAULT (and server-card) bids a live authorization may exist. → Add `bids.payment_method` (missing from data-model). On a timeout or 5xx, retry `createAuthOrder` with the same `PayPal-Request-Id = bid.id` (safe replay; S3 proved replay for capture only, so add an order-create replay test). For non-wallet PENDING_APPROVAL bids older than 2 min, the cron replays the same request id: if that returns an authorization, void it; then mark the bid ABANDONED.
- **[MAJOR]** The declined-hold end state is undefined. "Hold declined → 422 HOLD_FAILED, bid not HELD" leaves the row in PENDING_APPROVAL, which the cap sums and the abandon cron then mislabel. Its `idempotency_key` is also burned, so a retry with the same key replays the failure (see HF-019). → Transition PENDING_APPROVAL→ABANDONED with `void_reason`/`error_code=HOLD_DECLINED`, or add a `FAILED` status to the bid state machine. Also handle order status `PAYER_ACTION_REQUIRED` (3DS on a vaulted MIT hold) as HOLD_FAILED.
- **[MAJOR]** Store the authorization time for the 66 h guard (Q#15). Seeded bids have backdated `placed_at` and raised bids have fresh holds, so `placed_at` is the wrong clock for the honor period. → Add `bids.authorized_at` = the PayPal authorization `create_time`, set by every path that reaches HELD (HF-014/015/018). HF-027 computes hold age as `now − min(authorized_at)` over HELD bids. This resolves Q#15.
- **[MAJOR]** Biddable needs a time check as well as status (Q#5, Q#6). → New bids: `status='OPEN' AND now() < window_closes_at`. No brand-new bids during ROUNDS; ROUNDS accepts raises only (see HF-018). This keeps the nudged book closed and the hold-age math simple. Error `WINDOW_CLOSED`. This resolves Q#5 and Q#6.
- **[MAJOR]** A mandate can't be found from a bid (Q#19). Without `bids.mandate_id`, "sum of live holds for the mandate" (locking rule 3) has no defined set of rows. → Add `bids.mandate_id uuid null`. Set it when the bid is placed under a mandate (agent with mandate, MCP VAULT, rounds auto-raise, roll; for intent bids, `intent.mandate_id`). Bids a shopper places by hand on the offer page carry no mandate unless the shopper opts in from W13. This resolves Q#19.

- **[MAJOR]** Wallet approve-then-authorize is unproven in our sandbox. Only a competitor's spike (tipping-point, first-principles §4) shows it. ## HF-018: Raise bid (new hold first, then release)
- **[BLOCKER]** There is a window where both holds are HELD, so the shopper is charged twice. Between step 4 (new bid HELD) and step 6 (old HELD→VOIDING), both bids are HELD. A Clear in that window ranks both, both can WIN, and the shopper is captured for two units. If step 6's void then fails, the old bid stays HELD and in the book indefinitely. → Insert the new bid as PENDING_APPROVAL and get the PayPal hold. Then, in **one** transaction:
  1. `SELECT … FROM listings … FOR SHARE` and re-check that it's raisable;
  2. old `HELD→VOIDING` (conditional);
  3. new `PENDING_APPROVAL→HELD`;
  4. commit.

  Call `pp.void` on the old authorization only after commit. If any step in the transaction affects 0 rows (Clear, a watcher void, a shopper cancel or a pause won the race), roll back and void the **new** authorization instead. The old bid leaves the book atomically, so a failed void can't put it back.
- **[BLOCKER]** Two concurrent raises of the same bid each exclude the old hold from the cap, both get new holds, and only one swap can win. Without the swap above, both new bids end up HELD. → Put `replaces_bid_id` on the new bid with `UNIQUE (replaces_bid_id)`. The second concurrent raise fails on insert with 409 `STATE_CONFLICT`, before PayPal. This resolves Q#17: the new row points to the old one, which also enforces a single successor.
- **[MAJOR]** The new bid must inherit the old bid's fields. → Copy `release_if_cheaper`, `mandate_id`, `intent_id`, `source`, `payment_method` and the nudge-mute flag. If `release_if_cheaper` is on and `amount > products.best_public_price_cents` (a price-drop void can race the raise), reject before the hold with `422 PRICE_DROPPED`, and W21 shows the price-dropped variant.
- **[MAJOR]** When raises are allowed, and what happens after rounds end. ROUNDS has no "ended" state, so raises would keep changing the book while the brand is in the Clear modal (409 loops). → Raisable = `(status='OPEN' AND now() < window_closes_at) OR (status='ROUNDS' AND now() < rounds_end_at)`. HF-036's stop must set `rounds_end_at = now()` (cross-track, B). This relates to Q#6 and Q#7.
- **[MAJOR]** The payment method for the new hold isn't specified. → VAULT (CIT if the shopper is present, MIT for the rounds agent) if the shopper has a vault. Otherwise return `{status: PENDING_APPROVAL, approveUrl}` and finish the swap on the HF-015 return. Card-field shoppers get a vault on their first hold (if S7 confirms).
- **[MINOR]** Step 3 calls `mandates.authorize` unconditionally. → Call it only if `bid.mandate_id` is set; a manual raise on the offer page has no mandate.
- **[MINOR]** "Retry on failure; nightly sweeper is backstop": the sweeper only covers HELD bids. → Point to the VOIDING retry added in HF-016/HF-034.

## Top 5 risks for the track
1. **Live-rounds raises can double-charge or leave holds dangling (HF-018, HF-014, HF-038).** "New hold, then mark old VOIDING" leaves both bids HELD while Clear can rank them, and every "check, call PayPal, then mark HELD" path races Clear. The fix is one pattern used everywhere: PENDING row → PayPal → a single finalize transaction with `FOR SHARE` on the listing (and mandate), an atomic swap for raises, void-the-new-hold on a lost race, and the `one_held_bid` / `UNIQUE(replaces_bid_id)` indexes. Build it once in `core/bids.ts#finalizeHold()` and reuse it in HF-014/015/018/052/053.
2. **The card-fields flow is unproven and differs from the spikes (HF-014/019).** The browser flow is order → card submit (maybe 3DS) → authorize, but everything proven so far is a server-side raw test card. Spike S7 (card fields + vault + authorize, CIT vault hold, void idempotency) before 10:00 Nov 11. The fallback is a labelled server-side sandbox test-card button.
3. **The schedule doesn't fit.** C's P0 is 35 h against about 25 h of focused time, and the HF-014 → 018 → 038 chain finishes around 03:00 Nov 12, after the 22:00 video milestone. It waits on A's 11 h foundation chain and B's HF-036. Mitigations: the splits and demotions below, `voidBid()` moved into HF-014, fixture-first contracts with A (transition/audit/pp interfaces) and B (nudge row), and recording the video in the 05:00–07:00 buffer.
4. **Agent confirmation bypass (HF-040).** Without server-stored pending actions and a confirm endpoint, the LLM effectively authorizes holds and can change the amount. That's a correctness bug and a judging liability ("agents choose, code decides").
5. **Schema gaps that block C (owned by A in HF-002).** The `bids` table is missing `payment_method`, `mandate_id`, `authorized_at`, `replaces_bid_id UNIQUE`, `utm_source` and a declined-hold state. `mandates` is missing `needs_payment_method`, and `agent_messages` is missing `shopper_id`.
