## HF-009: Channel3 client, product search proxy and exact-match gate
- [MAJOR] The gate assumes every offer carries a GTIN (`offer GTIN equals product GTIN`, 06 §Logic 3; api.md webhook example has `data.gtin`, `offer.merchant`, `offer.priceCents`). Channel3's documented model is different. The Product fields (`id, title, brands, images, offers, variants, structured_attributes…`) don't list `gtin`/`mpn`. An Offer is `{url, domain, price{price, currency}, availability, condition}` with no GTIN and no merchant name. A product subscription is pinned to one product **variant `selection`** and **up to 25 domains** (02-sponsor-primitives-a §3.1–3.2). The api.md payload shape is invented. → In the first 30 minutes, make one live `search` and one `GET /v1/products/{id}` call and record them as fixtures. Then define the gate as two stages. **At listing creation:** GTIN/MPN from `structured_attributes` (or entered by hand) plus brand. **Per offer / webhook:** Channel3 product id + variant equal to the listing's, `condition == "new"`, `domain` in the brand allowlist, `currency == "USD"`. Rewrite the api.md webhook example from the real payload.
- [MAJOR] Colour/variant isn't modelled. XM5 Black and Silver are variants of one Channel3 product, and a subscription watches one variant. Without a variant key, a cheaper Silver offer voids Black bids (not the exact product) or is missed. → Add `products.channel3_variant` (or one `products` row per variant id), show the variant in the wizard (HF-013), and pass it in the subscription `selection`.
- [MAJOR] Allowlist storage is still a spec question (Q#16). The proposed "per-brand JSON config" isn't queryable by the watcher and can't be shown in the seed or README. → Resolve Q#16: `brands.authorized_domains text[]` (max 25, which matches the subscription domain cap and the "watches 25 stores" story in HOLDFAST-SPEC §3.2). Seed it in HF-045 and reuse it as the subscription's domain list. W11 editing stays P1 (HF-056). Add the column to HF-002 now.
- [MAJOR] Resolve Q#18 → store `channel3_subscription_id` on `products` (one subscription per product+variant, as 06 §Logic 1 says). `listings` references it. Publish (HF-012) reuses an existing subscription and doesn't create duplicates, which would duplicate webhook events and voids.
- [MINOR] Prices come back as decimals (`price.price`). → Convert to cents once in the client with `Math.round(price * 100)`, and table-test 279.99 and 0.1+0.2-style values.
- [MINOR] "Cache aggressively" conflicts with Channel3's caching rule (cache IDs only; prices and buy URLs are unstable). → Cache product identity forever. Refresh price and offers with the **free** detail endpoint (`GET /v1/products/{id}`) on the 10-minute rule. Spend search credits only on wizard and agent searches.
- [MINOR] `GET /api/products/search` burns credits and has no auth noted. → Require a brand or shopper session, rate-limit it (shared HF-006 limiter), and add a `CHANNEL3_MODE=live|fixtures` env switch for CI and clean-clone setup (HF-049).

## HF-042: Price watcher: Channel3 webhook, auto-void, labelled replay
- [BLOCKER] **The demo price-drop beat would wipe out the demo book.** `release_if_cheaper` defaults to **on** (data-model). SIM bids are seeded at "$189–$249, peak $215–$225", and the narrative event is "Best Buy now sells this at $219" (06 §Logic 6). A drop to $219 voids every HELD bid above $219 on that product: roughly half the 280 SIM bids, each a real sandbox void. After that, beat 5 ("Clear 240, cutoff $219, $54,240") can't happen. → Pick the event and the seed together. **Recommended:** replay a drop on the demo listing to a price just under **one foreground bid** (e.g. Claude Desktop bid at $249, drop to $245). Seed SIM bids above that price with `release_if_cheaper=false` ("wants it from the brand"), so the void hits ≤ 3 bids. Then recompute the beat 5 numbers *after* the drop. Add an acceptance criterion: "demo:price-drop voids exactly N bids (N printed by the script) and the post-drop simulate(240) still matches the video script".
- [MAJOR] Void idempotency for non-Clear voids (Q#14). The watcher voids outside Clear, but the void `PayPal-Request-Id` is defined as `settlement.id`. → Resolve Q#14: every void, from any path (cancel, price drop, raise-replace, expiry, pause), first inserts a `settlements` row (`action=VOID`), protected by `unique(bid_id, action)`, and uses its id as the request id. Add `settlements.origin` (`CLEAR|CANCEL|PRICE_DROP|REPLACED|EXPIRY|SWEEP`) so W08 counts only `CLEAR` rows.
- [MAJOR] Bids can get stuck in VOIDING. If `pp.void` returns 5xx/timeout after HELD→VOIDING, nothing retries. The HF-034 sweeper only looks for `HELD` on closed listings, so the hold dangles. → Retry the void with the HF-029 backoff, using the same settlement id. Extend the HF-034 sweeper to `status='VOIDING' AND updated_at < now()-5 min` (and `CAPTURE_FAILED`, see HF-046).
- [MAJOR] Async processing can lose an event. The handler returns 200 and then processes in-process; a Render restart or deploy in between leaves `webhook_events.processed_at IS NULL` forever. → On boot and every minute, reprocess `webhook_events WHERE provider='CHANNEL3' AND processed_at IS NULL`. The same loop serves the replay endpoint. Channel3 also requires a 2xx within 15 s; the fast-200 handling is right.
- [MAJOR] Race with Clear. "WON bids during CLEARING are not voided" relies on HF-027 reading bids in a way that blocks the watcher. If Clear reads `status='HELD'` without row locks, the watcher can flip a bid to VOIDING after Clear's snapshot and before it writes WON/LOST. The winner set and `expectedGross` are then wrong, and a "winner" has no hold. → In HF-027, `SELECT … FOR UPDATE` the HELD bids inside the Clear transaction. In the watcher, make the conditional update `UPDATE bids SET status='VOIDING' FROM listings l WHERE bids.id=$1 AND bids.status='HELD' AND l.id=bids.listing_id AND l.status IN ('OPEN','ROUNDS')`. Add a race test in HF-047: parallel replay + Clear.
- [MAJOR] Race with raises and auto-raises. A raise that started before the drop inserts a new HELD bid above the new public price after the watcher's SELECT, so it survives. Separately, HF-038's auto-raise can raise a bid above the known public price, which contradicts "the agent protects its owner". → (a) After voiding, the watcher re-runs the selection until it returns zero rows. (b) In HF-038/HF-018, when the actor is an agent (`BUYER_AGENT`/`SIM`/`MCP` with mandate) and `release_if_cheaper` is on, refuse to auto-raise above `products.best_public_price_cents` and ask the shopper instead.
- [MAJOR] `best_public_price_cents` only ever goes down ("update if lower"). A price **rise** or an offer leaving stock leaves the anchor stale. The anchor then shows on the offer page and in `publicOffer`, and `demo:reset` can't restore it. → On every event, recompute the best price from the free detail endpoint (cheapest `new`, `InStock`, allowlisted, USD offer), not by min(old, new). `demo:reset` restores it the same way.
- [MINOR] promoteNext (HF-031) can promote a reserve (LOST) bidder whose bid is now above the public price and who opted into release. → In HF-031 step 3, skip reserve bids with `release_if_cheaper AND amount_cents > products.best_public_price_cents`.
- [MINOR] Signature verification details are missing. → Store the Channel3 webhook HMAC secret in env (`CHANNEL3_WEBHOOK_SECRET`) and compare in constant time. The replay endpoint skips signature checks but requires admin and stamps `data.replayed=true` in `webhook_events`/audit, so the "replayed event (demo)" label comes from data and isn't hard-coded in the UI.
- [MINOR] Q#27: in-app plus MCP `my_bids` delivery is enough for P0. → Accept, but the in-app release event (W15/M06/W21) must include the affiliate link **and** the disclosure (HF-009). The README should say email/push is P1.
- [MINOR] Scope trim. The "Channel3-outage banner" and spec 06's "nightly poll as backup" aren't needed for the demo. → Move the outage banner to P1 and the nightly poll to README-only. Keep the replay path P0 and **build it first** (S5 is unproven).

## HF-044: MCP server (`/mcp`) with get_book, place_bid, cancel_bid, my_bids, raise_bid
